digi2 Essentials v1.0

Component library for Webflow. One script tag, modular, on-demand loading.

Installation

Single script tag in Webflow → Site Settings → Custom Code → Head Code:

<!-- Load only what you need via d2-* attributes -->
<script
  src="https://cdn.jsdelivr.net/gh/Digi2-Agency/digi2-essentials@latest/dist/digi2-loader.min.js"
  d2-gtm="GTM-XXXXXXX"
  d2-popups
  d2-cookies
  d2-forms
></script>

Per-Page Modules

Put the loader once in the global site head, then request modules per page so each page only fetches what it uses. Drop a declaration element in the page’s custom code — the loader scans the page on DOM-ready and loads exactly those modules.

Site Settings → Head (global, every page) script digi2-loader.min.js ← no module flags needed
Page custom code (per page) tag <digi2-module d2-forms d2-popups> ← only this page loads forms + popups 
<!-- Site Settings → Custom Code → Head (once, all pages) -->
<script src="https://cdn.jsdelivr.net/gh/Digi2-Agency/digi2-essentials@latest/dist/digi2-loader.min.js"></script>

<!-- Page Settings → Custom Code (per page) -->
<digi2-module d2-forms d2-popups></digi2-module>

Two forms, same result

<!-- Custom element with d2-* flags -->
<digi2-module d2-forms d2-popups d2-cookies></digi2-module>

<!-- Or a space/comma list on any element -->
<div d2-modules="forms popups cookies"></div>
ℹ︎

Flags on the loader tag and every <digi2-module> on the page are merged and de-duplicated. You can still keep global modules on the loader tag and add page-specific ones with the element. d2-gtm="GTM-XXX" and d2-ab-tests="configName" work on the element too.

✓

Calling a module’s API also auto-loads it on demand (e.g. digi2.forms.create()). Use <digi2-module> when you rely on declarative features (d2-show-popup, consent masters, auto-format) that need the module present without a JS call.

Responsive Attributes

Any value-bearing d2-* attribute supports per-breakpoint overrides:

<div d2-animation-direction="left;up@911"></div>
// "left" by default; "up" once innerWidth ≤ 911

<div d2-animation-distance="12px;24px@1200;40px@600"></div>
// 12px default; 24px ≤1200; 40px ≤600

Format: entries separated by ;. An entry with no @ is the default; value@<maxWidthPx> activates when window.innerWidth <= maxWidthPx. The smallest matching breakpoint wins.

Modules that need to react mid-resize (interactions, animate, popups) automatically re-apply state when the active bucket flips. Lower-traffic modules pick up the new value on the next event tick.

JS API for module authors / power users:

digi2.parseResponsive(raw)         // → { default, bps: [{ max, value }] }
digi2.resolveResponsive(parsed, w)  // → string at width (innerWidth if w omitted)
digi2.attr(el, name, fallback)     // → resolved string for that el+attr
digi2.on('responsive:change', fn)   // fires when active bucket flips

Locking width across breakpoints

d2-static-width pins an element to the widest content it has shown, so swapping values causes no layout shift, and anchors shorter content to one edge. The anchor takes the same per-breakpoint syntax as everything else:

Any element → Name d2-static-width Value left;right@728

Left normally, right at 728px and below. A value that doesn't apply at the current width clears the anchor rather than leaving the previous breakpoint's alignment in place, and the locked width is re-measured when the breakpoint flips — a width measured on desktop would otherwise cage the element on mobile, where the same text wraps narrower. Flex containers are anchored with justify-content instead of text-align.

Requiring a few pages first

openAfterPageViews: 2 is the trigger — it opens the moment the second page loads. When the condition is "they have been around a bit and stayed a while", use minPageViews instead: a gate that combines with whatever trigger you already have.

digi2.popups.create('oferta', {
  openAfterDelay: 30,     // 30 s on the page…
  minPageViews: 2,       // …and not before the second page
})

It holds back automatic opens only — a click on d2-show-popup or a digi2.popups.show() still opens it, because a button that does nothing on page one is worse than a popup shown early. The count lives in sessionStorage and is one per document, however many popups the page carries.

One popup at a time

Two modals on screen at once is never right: whichever one the visitor closes leaves the other behind, and it reads as a close button that did nothing. Nothing ever opens on top of what is already up — who yields depends on who asked for it.

Opened byWith another popup on screen
The page — openAfterDelay, exit intent, scroll, idle, page views, a sequence stepWaits. It parks itself and opens ~0.6 s after the screen frees up. A promo never covers the form the visitor is filling in, and never closes it either
The visitor — d2-show-popup, openTriggerSelector, digi2.popups.show(), an intercepted linkWins. What is on screen closes first; this one opens once that close has finished, so the two never overlap even for a frame

An open lightbox counts as a busy screen too — for automatic opens only. They park and come ~0.6 s after lightbox:close, and a sequence step waits the same way. A popup the visitor asks for (a button inside the gallery, d2-show-popup) still opens over it.

On a page without d2-lightbox nothing waits: popups ask the loader whether the lightbox module is loaded before asking it anything, so the check neither fetches the module nor mistakes the loader’s placeholder for an open gallery (fixed in v1.8.2 — on v1.8.1 automatic popups never opened on such pages).

A deferred popup re-runs every check when its turn comes — a dismissal cookie written while it waited, a schedule that has since closed, a canShow() veto. It waits for a free screen; it does not book a guaranteed appearance.

Shared scroll lock

Popups and the lightbox hold one page scroll lock, digi2.scrollLock. Each of them used to remember body.style.overflow on open and write it back on close, so a popup opened over the gallery remembered the gallery's hidden — close the gallery first, then the popup, and nothing was open on a page that would not scroll. The shared lock keeps a set of owners: the first one in remembers the page's own value, the last one out puts it back, in whatever order they close.

digi2.scrollLock.acquire('my-overlay')   // overflow: hidden — idempotent per owner
digi2.scrollLock.release('my-overlay')   // last owner out restores the page's value
digi2.scrollLock.isLocked()
digi2.scrollLock.owners()              // e.g. ['lightbox', 'popup:form#1']
CaseBehaviour
Popup and lightbox closed in either orderThe page scrolls again only after the last one closes, and gets back the value it had before the first one opened
The same owner acquires twiceNo-op — one release undoes it
Release by an owner that holds nothingNo-op — never unlocks more than was locked
The close animation never reports its endThe popup settles on its own transitionend or on a timer just past the animation duration, whichever comes first, and releases the lock. A ✕ pressed mid fade-in closes the popup rather than being ignored
digi2.popups.destroy() on an open popupThe popup is hidden and its lock released. No popup:close / onClose — nobody closed it — but a popup parked behind it gets the screen

Your own overlay script (a full-screen map tooltip, a menu) should use digi2.scrollLock with its own owner name instead of saving and restoring overflow by itself — otherwise it can write a stale hidden back over the shared lock.

Waiting for an Intro

A page that opens with a loader or intro animation has a problem with timed popups: openAfterDelay: 7 counts from page load, so on a six-second intro the popup opens against a curtain the visitor can’t see past — and by the time the animation lifts, it has been sitting there for a second already. startOn moves the starting line. Every trigger the page decides on its own waits for the milestone; every trigger the visitor reaches for stays live.

digi2.popups.create('promo', {
  popupSelector: '#popup-promo',
  startOn: 'intro:done',   // wait for the animation
  openAfterDelay: 7,        // then count seven seconds
})

// …and wherever the animation finishes:
digi2.signal('intro:done')

The name is yours — startOn waits for whatever string you pass, so one page can gate on 'intro:done' and another on 'video:ended'.

Add custom attributes to the popup wrapper:

Popup Wrapper → Name d2-popup-start-on Value intro:done
Popup Wrapper → Name d2-popup-start-timeout Value 12

The timeout attribute is optional — it only tunes the failsafe below. data-d2-popup-start-on also works.

Three ways to say “go”

Whoever owns the animation is rarely whoever owns the popup, so the milestone is accepted from all three:

FromCodeNotes
digi2 busdigi2.signal('intro:done')Prefer this. It is remembered: a popup created after the signal opens its gate immediately instead of waiting forever
windowwindow.dispatchEvent(new CustomEvent('intro:done'))For animation code that knows nothing about digi2
documentdocument.dispatchEvent(new CustomEvent('intro:done'))Same, if that is where your code already dispatches

digi2.emit() reaches only whoever is already subscribed. The popups module is fetched asynchronously, so an intro that finishes first would emit into an empty room — which is exactly the race digi2.signal() exists to remove. digi2.when(name, fn) and digi2.signalled(name) are the read side, for your own code.

The failsafe

An animation can fail to arrive: a plugin that 404s, a reduced-motion visitor whose intro never plays, a JS error three lines earlier. None of that should cost the site every automatic popup on the page, so the gate opens on its own after ten seconds.

ValueBehaviour
startOn: 'intro:done'Failsafe at 10 s
startOn: { event: 'intro:done', timeout: 12 }Failsafe at 12 s
startOn: { event: 'intro:done', timeout: false }No failsafe — waits indefinitely
d2-popup-start-timeout="never"Same, from the attribute

Set the failsafe a little longer than the animation actually runs, not shorter: a gate that opens early is the bug you were fixing.

What waits and what doesn’t

TriggerBehind the gate?
openOnLoad, openAfterDelay, openOnExitIntent, openAfterPageViews, openAfterIdle, openAfterScrollPercent, openAfterScrollPastElement, openOnScrollSpeed, openOnTabBlurWaits. The page decided these on its own

Scheduled Popups

Limit a popup to a date/time window. It’s a gate, not a trigger — your triggers still run, but the popup won’t show outside the window. Times use the visitor’s local timezone.

digi2.popups.create('promo', {
  schedule: { from: '2026-07-01 18:00', to: '2026-07-15 23:59' },
})

// open-ended — drop either bound
schedule: { from: '2026-07-01 18:00' }   // from then on
schedule: { to:   '2026-07-15 23:59' }   // until then

Add a custom attribute to the popup wrapper:

Popup Wrapper → Name d2-popup-schedule Value 2026-07-01 18:00, 2026-07-15 23:59

The popup still needs its create() embed (see Webflow Setup) — the schedule can live on the attribute or in the embed.

Campaign Targeting

Scope a popup to the traffic it was written for. Like scheduling, this is a gate rather than a trigger: your triggers still run, the popup just stays shut for everyone else.

digi2.popups.create('promo', {
  utm: 'utm_source:facebook|instagram',   // only this traffic
  utmExclude: 'utm_medium:cpc',            // never this traffic
  utmCookie: true                          // remember it past the landing page
})

Add a custom attribute to the popup wrapper:

Popup Wrapper → Name d2-popup-utm Value utm_source:facebook|instagram
Popup Wrapper → Name d2-popup-utm-exclude Value utm_medium:cpc

data-d2-popup-utm works too. The popup still needs its create() embed.

Value format

FormMatches
utm_source:facebookExactly that value, case-insensitive — google never matches googleads
utm_source:facebook|instagramEither one — pipe is OR
utm_campaignAny non-empty value for that key
utm_campaign:*Same as the bare key
ref:partner-aAny query parameter, not only utm_*

It survives navigation

A campaign parameter only exists in the URL of the landing page. A gate reading just the query string would go dark the moment the visitor clicks through — taking openAfterDelay, openAfterPageViews and sequences with it. So the module reads the URL first and falls back to a cookie it writes on first touch, under the same name the forms module uses (utm_source, …) — one shared value, not two copies. Set utmCookie: false to skip that write.

Where the gate sits

URL filters first (they block everything, including digi2.popups.show()), then traffic, then schedule, then promotion state, then a d2-ma condition on the overlay (parked; d2-ma resumes it), then canShow.

A traffic mismatch is not parked for showIfPending() — unlike a promotion ending or another popup closing, it can never resolve during the visit. It does stop show() and d2-show-popup clicks: a popup written for one campaign shouldn't open for someone else just because a button was clicked. In a sequence, a step that doesn't match is skipped rather than waited on. These two attributes are read raw rather than through the responsive parser, because a campaign value may legitimately contain ; or @.

Sequences

Spread popups across a whole visit. openAfterDelay restarts at every page load, so it can't express "and three minutes after that one is closed" — a sequence can, because its clock lives in sessionStorage and survives navigation.

One popup, shown several times

digi2.popups.create('promo', {
  popupSelector: '#popup-promo',
  cookieName: null,
  sequence: [4, { after: 60, afterPageChange: true }, 180, 180]
})

Numbers are seconds: the first counts from arrival, each next one from the close of the previous showing. An entry may be an object when a step needs afterPageChange — wait until the visitor opens another page, and only then start counting.

This implies setCookieOnClose: false: a popup that repeats can't treat "closed" as "done with it", or every later showing would be skipped and you'd see it exactly once.

A chain of different popups

digi2.popups.sequence([
  { popup: 'welcome',    after: 4 },
  { popup: 'oferta',     after: 60, afterPageChange: true },
  { popup: 'newsletter', after: 180 }
])

Give every popup in a chain its own cookieName. The default is the same popup_clicked for all of them, so closing step one would mark the rest as seen and the chain would skip to the end — the module warns in the console when it spots that.

status() returns { step, popup, elapsed, dueAt, waitingForClose, done } for debugging; stop() halts the chain on this page, reset() starts it over.

Reset After Success

Webflow's success state is terminal: it hides the <form> and leaves .w-form-done up until the page reloads. Anywhere people submit more than once — a booking widget, "report another", a form inside a popup that reopens — that's the wrong resting state.

// or without registering a form at all
digi2.forms.autoReset(30)              // every .w-form on the page
digi2.forms.restore('#contact-form')   // right now, e.g. from a popup's onOpen

Add a custom attribute to the form wrapper — the element Webflow gives the w-form class:

Form Block (.w-form) → Name d2-form-reset Value 30

Seconds. A bare attribute with no value means 30. No create() embed needed for this one.

What a restore does

StepDetail
Clears the fieldsform.reset()
Keeps hidden tracking valuesUTM_*, GCLID, IP_ADDRESS were written by JS, so their DOM default is empty — a plain reset would silently un-attribute every later submission. They're carried across

Drops validation error stylingLeft over from the submission

An error state is treated differently: only the message is cleared and every field keeps what the visitor typed — wiping a filled-in form because the server hiccuped would be its own bug. Form Events & Leads

A form produces four distinct signals, and telling them apart is the difference between measuring intent and measuring outcome.

EventFires when
form_submitVisitor clicked Submit and client-side validation passed
form_errorClient-side validation refused it
form_submit_successWebflow confirmed the submission (.w-form-done)
form_submit_errorWebflow refused it (.w-form-fail) — spam guard, plan limit, network

The funnel — where people drop out

Submitted or not says nothing about why. Three more events, in their own forms-detail group, answer that.

EventFires
form_startFirst interaction with the form — once per visit, not per pageview
form_field_interactionThe first change of each field, with field_name and field_type
form_submit_clickThe button was pressed, before validation ran

Full funnel: form_start → form_field_interaction → form_submit_click → form_submit / form_error → generate_lead / form_submit_error. form_submit_click minus form_submit is "pressed the button and got bounced by validation", and the field people stall on shows up as the last form_field_interaction before they give up.

Never a value. These carry the name and type of a field, never its contents — no emails, phone numbers or message bodies, which is both a GDPR line and a GA4 terms line. form_field_interaction fires on a field's first change rather than every blur, or a 12-field form would push a dozen events per visitor. Drop the whole group with d2-datalayer-disable="forms-detail" without touching the conversion events.

Where generate_lead fires

By default, on form_submit — the click. Webflow hasn't sent the request at that point, so a refusal still counts as a conversion. Since generate_lead is usually a key event in GA4 and imported into Google Ads, that is what the bidding algorithms learn from.

Field values are never pushed — no emails, phone numbers or message bodies, only names of things and flags. What binds, and how

Every scalar field of the contract binds by its own name — name, project_name, city, city_line, address_line, rooms, area, floor, beds, max_guests, description, rental_kind, timezone, latitude, longitude, min_units, max_units, payment_mode… — so a page is never limited to a list somebody hardcoded. Four read differently:

priceThe entry's own price.price in the entry's own currency, through the same Intl formatting as the quote. The module computes no amount here either.

Paging, and a page that was refused

Paging is limit and offset. The first page replaces the rows; every later one is appended, so the guest keeps what they were already reading. A page that was refused leaves the offset where it was — the next click asks for that same page again instead of skipping it — and says why in [d2-booking-results-message], in the module's own words, with [d2-booking-results-empty] taken down: "nothing found" and "we could not ask" never stand together. A 400 on this route is about what the filter asked for: the period (invalid_stay), or the period and the city once the search named one (invalid_search). A 429 is the one refusal that holds the button: it waits exactly Retry-After seconds (read up to 3600), because opening it at once only buys the next 429. With two lists waiting, the search opens when the last wait ends. A field built twice counts as visible when it has an offsetParent or client rects, so a copy in a position: fixed drawer is the one the guest sees.

The rules come from the answer, not from the page

Field of the answerWhat the calendar does with it
busyMarks the nights nobody can book. A range can never be dragged across one — every night between the arrival and the departure is checked, not just the two ends. Each entry says its kind: booking (someone's stay, refused as period_taken) or blackout (the owner closing the days, refused as blackout_overlap), so the sentence the guest reads is the true one.
min_units / max_unitsBound the number of nights. A departure outside them is refused with the number in the sentence ("the shortest stay is 3 nights").
lead_time_hoursA stay starts at local midnight and the backend holds that moment against now plus that many hours, so the first day on offer is the first midnight after it, in the rental's time zone. allowed_unitsThe calendar counts nights, so it always sends unit: "day", whatever comes first in the list. A product without day cannot be booked on a calendar: every day answers unit_not_allowed and the console says why.
buffer_minutesWidens a booking on both sides before the nights are counted, and refuses the nights it took as buffer_conflict. A blackout is never widened — it is an exact window. An unknown kind is counted as a booking.
timezoneThe zone a square belongs to. Busy periods arrive as UTC instants and are converted with Intl, then counted in whole days — no daylight saving change can move a night.

That is the whole of what the answer carries about the rules. There is no check-in-day rule in the contract, so the calendar never closes a week day on its own — every day of the week is a possible arrival.

A busy period that ends at local midnight leaves its last date free: the guest who leaves that morning never slept there. So the first day of a taken period is still a possible departure — the two nights before a taken period are bookable, and a stay that would swallow the taken nights is not.

buffer_minutes is the gap between stays, so it only ever touches a booking. A blackout is an exact window: "renovation until 12:00" means the flat is free at 12:00, and the nights beside it stay bookable. That is how the backend counts it (rental_violations in services/rental_availability.py checks the widened stay against booking periods only), so a calendar that widened every period would grey out nights the backend would have taken — and the guest would see a closed square with no reason for it. A kind the module does not know is counted as a booking, buffer included: a night refused for nothing can be won back, a double booking cannot. Where two periods reach the same night, the overlap wins over the gap, so that night reads as taken rather than as a missing gap.

Two clicks make a stay

The first click is the arrival, the second the departure. A day before the arrival (or the arrival itself) starts over. A day the rules refuse says why in the live region and leaves the arrival where it is, so the guest never has to guess which half of the range the calendar dropped. Only a complete range reaches digi2.booking.select(): half a stay is not a stay, and a missing length never quietly becomes one night.

Booking — The Drawn Widget

<div d2-booking-widget></div>

An empty element is the whole setup. Inside it the module draws every part the page does not have: the calendar, the live region, the form (party row, guest fields, message slot and the submit button), the breakdown, the total and the deposit/balance. It is the quickest way to put a working booking on a page — and the fallback when a Designer only had time for a container.

Booking — Payment

Submit is the whole way: POST …/bookings creates the booking, then POST /bookings/<id>/checkout-session asks for the payment, then the browser goes to the address the answer carries. The checkout route takes no body — what is being paid, and where the provider comes back to, is the backend's business. Only an https address is followed (http://localhost while building): a redirect is the one thing a tampered answer could use.

One booking per request

The submit button is really disabled on the first click, and the attempt is kept under the key of what the hold stands on: the product, the stay and the party. A second submit is handed the answer of the attempt already running, and a retry after a payment hiccup pays the booking that already exists instead of holding the period twice. Change the dates or the party and it is a different stay, so a different booking.

A corrected contact follows the booking. When the name, e-mail or phone changed since the booking was made, the module sends them to POST /bookings/<id>/contact before paying, so the confirmation and the link reach the address typed last. The route is proved with a contact_token from the booking answer, which stays inside the module: it is never on the booking object, in an event, in the address or in the log. Without a valid token (404) nothing is paid and the guest is told the details can no longer be changed.

A lost answer is recovered. Every POST …/bookings carries an Idempotency-Key (UUID v4) tied to the hold — product, period and party — and at most 24 hours old, and the retry repeats the body that key was first sent with. A request that timed out here but landed there returns the same booking on retry, instead of being refused by the guest's own hold — even when the guest corrected their e-mail in between: the booking comes back and the corrected contact follows through /contact before payment. A phone or name the guest emptied is sent as null, which is what clears it. A recovered booking with status: "expired" is not paid: the guest is told, and the next submit is a new request under a new key.

booking:created carries the booking without customer_name, customer_email, customer_phone and customer_note, so a GTM listener pushing it to the dataLayer sends no guest data. Retry-After is read up to 3600 seconds everywhere: past ~24.8 days a timer overflows and would open the button at once.

Coming back from the checkout with the Back button re-opens the form: the browser may restore the page exactly as we left it, disabled button and all. The booking is remembered, so the next submit pays that one.

Booking — The Return Page

<div d2-booking-return></div>

The page the payment comes back to: …?booking=<id>&payment=<success|cancelled|balance_success|balance_cancelled>. One empty element is the whole setup — the module reads the booking id out of the address (or out of the element's own value when the page knows it), asks GET /bookings/<id>/status and says what became of it.

The card clears before the webhook lands, so the status is asked again after a longer wait each time — eight tries over about forty seconds — and then the block stops and says the payment is still being checked. A dead network, a 429 or a 5xx on the way is one more wait, not a verdict: this guest may have just been charged, and an error sentence would send them back to pay again. Only the last try, or an answer about the booking itself, ends it. A cancelled payment is read once and never polled: nothing is on its way, and a guest who closed the payment on purpose must not watch a spinner.

Subscribing to loaded after modules already loaded calls fn immediately.

Signals — milestones a late listener still hears

emit() reaches whoever is subscribed at that moment, which is the wrong shape for a one-off milestone like “the intro animation finished”. Modules are fetched asynchronously, so on a fast connection the listener subscribes after the milestone and waits forever, while on a slow one it works — a race that looks like a popup that sometimes never opens.

digi2.signal('intro:done')          // emit AND remember
digi2.when('intro:done', fn)      // run once: now if already signalled
digi2.signalled('intro:done')       // → true / false

when() returns an unsubscribe function and never fires twice. Used by startOn — see Waiting for an Intro.

Module Management

digi2.modules.check('cookies')                   // true / false
digi2.modules.list()                              // ['popups', 'cookies']
await digi2.modules.require('forms')              // load on demand
await digi2.modules.requireAll(['cookies', 'forms'])

Until a module arrives, digi2.popups, digi2.forms, … are the loader's stubs: each method loads the module, then runs the call and returns a Promise of the result.
